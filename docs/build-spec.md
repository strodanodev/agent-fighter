# Agent Fighter — Build Spec v1

*2026-07-14 · Confirmed decisions: 1v1 first (tag-ready architecture) · AI-generated sprites with consistency tooling · Core MvC-feel combat · TypeScript + PixiJS*

---

## 1. Product definition

A browser-based 2D fighting game that *feels* like a MUGEN/IkemenGO Marvel vs Capcom mod — fast, crunchy, sprite-based, combo-heavy — built on a custom lightweight engine with a modern, automated character pipeline instead of MUGEN's hand-authored CNS/AIR configuration.

**v1 scope:** 1v1 matches, local + online multiplayer, single-player vs AI, 4–6 character roster. Crypto ("insert coin" + wagering) is architecturally anticipated but ships in a later phase (see §9).

**Non-goals for v1:** tag/assist gameplay (architected for, not shipped), mobile touch controls, spectator mode, community character uploads.

---

## 2. Architecture overview

Three deliverables, one shared core:

```
┌─────────────────────────────────────────────────────────┐
│  @af/core — deterministic simulation (pure TS, no DOM)  │
│  fixed timestep · integer/fixed-point math · no Date/   │
│  Math.random · serializable GameState · seeded RNG      │
└────────────┬───────────────┬────────────────┬───────────┘
             │               │                │
      ┌──────┴─────┐   ┌─────┴──────┐   ┌─────┴──────┐
      │ @af/client │   │ @af/server │   │ @af/studio │
      │ PixiJS     │   │ Node match │   │ character  │
      │ renderer + │   │ relay +    │   │ authoring  │
      │ input +    │   │ result     │   │ web tool   │
      │ netcode    │   │ verifier   │   │            │
      └────────────┘   └────────────┘   └────────────┘
```

Monorepo (pnpm workspaces). `@af/core` is the crown jewel: it must run identically in the browser (gameplay), in Node (server-side match verification), and headless at faster-than-realtime speed (AI training, replay validation, tooling preview).

### 2.1 Determinism rules (non-negotiable, enforced by lint + CI replay tests)

- Fixed timestep: **60 ticks/sec**, simulation advances only via `step(state, inputs) → state`.
- All positions/velocities in **fixed-point integers** (e.g. 16.16), never floats — float math diverges across browsers/CPUs and breaks rollback + server verification.
- No `Math.random` — one seeded PRNG living inside `GameState`.
- No `Date`, no DOM, no async inside the sim.
- `GameState` is a flat, serializable structure with cheap snapshot/restore (structuredClone or manual copy of typed arrays) — required for rollback.
- CI gate: replay a recorded input log 1000× and cross-environment (browser vs Node) and assert bit-identical final state hashes.

### 2.2 Entity model (this is what makes it "tag-ready")

Do **not** hardcode "player 1 fighter" and "player 2 fighter". The sim owns a pool of **entities** (fighters, projectiles, effects), and each *team* owns a list of fighter entities with one flagged **active**. In v1 each team's list has length 1. Tag/assists later = spawn a second fighter entity per team + a swap/assist-call mechanic — no engine rewrite.

Every fighter entity consumes an **`InputFrame`** (bitfield: directions + 6 buttons) from an **input source** interface. Human local input, remote network input, AI policy, and replay playback are all just implementations of `InputSource`. This single abstraction unifies single-player, multiplayer, bots, and replays.

## 3. Character data format (the CNS/AIR replacement)

One character = one folder = one versioned bundle:

```
characters/ryu-analog/
  character.json      # manifest: name, health, walk/dash speeds, weight/gravity,
                      # meter gain rates, palette list, version hash
  moves.json          # the frame-data table (see below)
  cancels.json        # cancel graph: which moves cancel into which, on-hit/on-block/whiff
  atlas.png / .avif   # packed sprite atlas (generated by studio, never hand-made)
  atlas.json          # frame rects + pivot points
  audio/              # hit sfx, voice, mapped by move id
```

### 3.1 `moves.json` — the heart of the system

Every action (idle, walk, jump, each normal, special, super, hitstun, knockdown…) is a **Move**: an ordered list of **frame steps**, each declaring everything the sim needs:

```jsonc
{
  "id": "5HP",                       // numpad notation as canonical move ids
  "input": "HP",                     // or motion: "236P" for specials
  "type": "normal",                  // normal | command | special | super | system
  "physics": { "selfVelX": 0 },      // per-step velocity impulses allowed too
  "steps": [
    { "frames": 4, "sprite": "hp_startup_1", "phase": "startup",
      "hurtboxes": [[-20,-90,40,90]] },
    { "frames": 3, "sprite": "hp_active_1", "phase": "active",
      "hurtboxes": [[-20,-90,40,90]],
      "hitboxes": [{
        "rect": [10,-70,55,30],
        "damage": 800, "chip": 80,
        "hitstun": 18, "blockstun": 12,
        "hitstopFrames": 8,
        "pushbackHit": 6.0, "pushbackBlock": 8.0,
        "launcher": false, "knockdown": false,
        "juggleCost": 1,
        "guard": "mid"                // mid | low | overhead | unblockable
      }] },
    { "frames": 9, "sprite": "hp_recovery_1", "phase": "recovery",
      "hurtboxes": [[-20,-90,40,90]] }
  ],
  "onWhiffCancelWindow": null,
  "meterGainWhiff": 2, "meterGainHit": 12
}
```

Design principles: **data, not code** — a character is 100% declarative; the engine interprets the table. No per-character scripting language in v1 (this is MUGEN's CNS trap). If a character truly needs bespoke logic later (e.g. a stance system), add a small allowlisted "behavior flag" vocabulary to the schema rather than embedding a scripting runtime. Schema is versioned + validated (zod), and the character bundle hash is part of match setup so both clients + server provably simulate identical data — this matters once money is on the line.

### 3.2 `cancels.json` — magic series as a graph

MvC chain rules (L→M→H→launcher, specials cancel from normals on hit/block, super cancels from specials) are one declarative graph per character: `{ from: "5MP", to: ["5HP","2HP","236P"], on: ["hit","block"] }`. Universal defaults (magic series template) defined once at engine level; characters override.

## 4. Combat system spec (core MvC feel)

- **Buttons:** 6 — LP/MP/HP, LK/MK/HK (classic MvC1/MvC2 layout). Keyboard + gamepad (Gamepad API) mappable.
- **Movement:** walk, forward/back dash, 8-way jump, super jump (tap down→up), double jump as per-character flag. Air dash as per-character flag (MvC identity move — include for at least 2 launch characters).
- **Chains:** magic series (any L → any M → any H → launcher `2HP`), configurable per character via cancel graph.
- **Launcher + air combos:** launcher pops up, attacker may super-jump follow (auto "jump-install" window), air chain L→M→H → finisher causing knockdown. **Juggle points system** (each hit has `juggleCost`, combo has a juggle budget) to bound infinites.
- **Specials:** motion inputs — 236 (QCF), 214 (QCB), 623 (DP), charge moves. Input buffer ~8 frames with lenient motion parsing (MvC is famously lenient; parser tolerance is a tunable).
- **Supers:** 1 per character in v1, costs 1 bar; meter builds on whiff/hit/being-hit. Super flash freeze frame. Meter max 3 bars (future DHC headroom — tag-ready).
- **Defense:** hold-back blocking (stand/crouch, mid/low/overhead logic), chip damage, **pushblock (advancing guard)** — it's core to MvC feel and cheap to implement (block + 2P → extra pushback), throws + throw tech (4/6 + HP at close range).
- **Combo/damage rules:** damage scaling per hit (e.g. ×0.9 compounding, floor 20%), hitstun decay in long juggles, combo counter UI.
- **Hitstop:** attacker+victim freeze frames on contact — this, more than anything, is the "crunch" that makes it feel like MvC. Tune obsessively.
- **Round flow:** best of 3, 99-second timer, round intro/KO/win poses are just Moves in the data format (`type: "system"`).

**Screen/camera:** single side-scrolling stage ~2.5 screens wide, camera tracks midpoint, corner logic, MvC-style vertical camera follow on super jumps. Stage = parallax layers + floor Y — deliberately simple, stages are set dressing not gameplay.

## 5. AI sprite pipeline + consistency tooling (the differentiator)

The confirmed pain point: AI image models generate gorgeous single images but drift across frames (proportions, palette, details). The pipeline is designed around **generate → normalize → verify → fix**, treating the model as an unreliable artist whose output must pass automated QC.

### 5.1 Pipeline stages

1. **Character sheet first.** Generate one canonical reference sheet (front/side/back, T-pose or fighting stance, fixed palette) per character. This sheet is the *contract* — every subsequent generation is conditioned on it (image-conditioning / reference-image modes of the gen model, e.g. character-reference features).
2. **Animation generation per move**, not per frame. Prompt for a full animation strip ("6-frame heavy punch sequence, side view, consistent character") or use pose-conditioned generation (ControlNet-style skeleton poses per frame — you author a rough pose skeleton per animation once per *archetype*, and every character reuses the archetype's pose track). **Archetype pose libraries are the big cost saver:** "shoto", "grappler", "zoner" pose sets get built once and reused across the roster.
3. **Normalization pass (deterministic code, no AI):** background removal → palette quantization to the character's locked palette (this fixes most visible inconsistency almost for free) → downscale to target sprite resolution with nearest-neighbor (pixelation makes small drift invisible — a genuine advantage of the MUGEN aesthetic) → auto-crop + pivot alignment (feet-anchor detection so the character doesn't slide between frames).
4. **Consistency verification (automated QC):** per-frame checks against the reference sheet — palette conformity %, silhouette height/proportion bounds, pixel-count-per-region sanity, optionally CLIP/embedding similarity score vs reference. Frames failing thresholds get flagged in Studio for regeneration (auto-retry with adjusted prompt) or manual touch-up.
5. **Auto-hitbox/hurtbox draft:** hurtbox from alpha-channel bounding boxes (subdivided into head/torso/legs bands); hitbox drafts from frame-diff against the previous frame (the region that *extends* during active frames is almost always the attack). Human adjusts in Studio; never hand-types coordinates.

### 5.2 Studio (the authoring web app)

Single-page web tool, same TS stack, embeds `@af/core` for live preview:

- **Generate tab:** prompt + reference-sheet management, per-move batch generation, QC scores displayed per frame, one-click regenerate failures.
- **Frames tab:** timeline editor with onion-skinning; drag frame durations; visual hitbox/hurtbox editing (drag rects on canvas); pivot adjustment.
- **Moves tab:** frame-data table editor (damage/stun/pushback/etc.), cancel-graph editor.
- **Test tab:** live playable preview vs a dummy (record/replay dummy actions) — because `@af/core` runs headless, the *actual game engine* renders the preview; what you see is exactly what ships.
- Exports the character bundle (atlas + JSONs) with a content hash. Bundles stored in object storage/CDN, referenced by hash at match time.

**Milestone truth-test:** character #1 may be built painfully; the tooling is proven when character #2 takes < 2 days end-to-end.

## 6. Rendering (`@af/client`)

- PixiJS v8, WebGL2 (WebGPU when available). Sprites from packed atlases; nearest-neighbor filtering for pixel crispness.
- Renderer is a **pure function of GameState** + interpolation — it owns zero game logic. It also renders *past* states seamlessly during rollback corrections.
- Juice layer (non-simulated, cosmetic only): hit sparks, screen shake on heavy hits, super flash cinematics, dust effects. Cosmetic particles live outside GameState so they don't burden rollback.
- Debug overlay: hitbox/hurtbox display, frame-advantage meter, input history — ship it in dev builds; it doubles as Studio's preview.
- Target: 60fps on integrated graphics on a 5-year-old laptop; total core bundle < 5 MB excluding character assets (characters lazy-load by hash).

## 7. Netcode & match server

### 7.1 Rollback (client)

- GGPO-style: send local `InputFrame` each tick (WebRTC DataChannel, unreliable+unordered, with input redundancy — resend last N inputs each packet); predict remote input as "same as last frame"; on receiving actual input, if mispredicted → restore snapshot, re-sim forward.
- Snapshot ring buffer ~10 frames; typical re-sim cost is 1–3 ticks — trivial for a 2-fighter sim.
- Adaptive input delay (0–3 frames) + rollback beyond it. Regional matchmaking targets < 100 ms RTT.
- Build the sim rollback-native from day 1 (snapshot/restore in the very first prototype). Retrofitting rollback is a rewrite; building on it from the start is cheap.

### 7.2 Server (`@af/server`)

Even in the free-play phase, matches run through a thin server (Node + uWebSockets/WebRTC signalling):

1. **Matchmaking + session setup:** pairs players, distributes character bundle hashes + RNG seed, brokers WebRTC (P2P inputs) — server relays inputs as TURN-style fallback when P2P fails.
2. **Input ledger:** both clients also stream their inputs to the server (reliable channel, non-latency-critical). Server stores the complete input log per match.
3. **Result verification:** at match end, server re-simulates the input log with `@af/core` (headless, faster than realtime — a 3-round match verifies in well under a second) and derives the result *itself*. Client-reported results are advisory only. This is the anti-cheat backbone that later makes wagering settlement trustworthy, and it costs almost nothing because the sim is deterministic and shared.
4. Desync detection: clients exchange periodic state hashes; on persistent mismatch, match voids (no settlement) and logs for debugging.

Cheating that verification can't catch (input-level bots/macros) is mitigated later by rate analysis + behavioral review; out of scope for v1.

## 8. Single-player AI

- AI = an `InputSource` implementation reading GameState and emitting InputFrames — zero special engine paths; the sim cannot tell a bot from a human.
- v1: **utility/FSM policy** with a per-difficulty *reaction delay* (e.g. 18 frames at easy, 6 at hard), intentional execution error rates, and per-character move-preference weights (data-driven, lives next to the character bundle). States: neutral (spacing via preferred-range scoring), offense (open combo attempts from a small combo book per character), defense (block/pushblock/tech with probability by difficulty), punish (whiff detection).
- The headless fast-forward sim enables **automated balance smoke tests**: bot-vs-bot batch runs to flag degenerate stats (infinite loops, unwinnable matchups) before humans playtest.
- LLM/agent personality layer (trash talk, adaptive strategy narration, "agent" branding) is a later, off-hot-path addition.

## 9. Auth & crypto (phased, summarized — details in architecture doc)

- **Phase A (with online launch):** Privy auth (embedded wallet + social login), profile, match history. No value transfer.
- **Phase B:** "insert coin" — on-chain deposit → off-chain credit ledger, credits gate ranked-match entry.
- **Phase C (gated on legal review):** P2P wagering via non-custodial escrow contract; settlement consumes the server-verified match result; both players' clients + server sign the input-log hash. Testnet/small-stakes first. Chain choice TBD (open question).
- The engine's only obligations today: match results must be server-verified (§7.2), match records must be signed + archived, and user identity flows through Privy IDs from the start.

## 10. Milestones

| # | Milestone | Definition of done |
|---|-----------|--------------------|
| 0 | **Sim skeleton** | Deterministic core: 2 rectangle fighters, walk/jump/one attack, hit detection, health, KO. Snapshot/restore + replay hash test green in CI. Local 2-player, one keyboard. |
| 1 | **It feels like MvC** | Full combat system (§4) with 1 real character (placeholder or first AI-gen art). Chains, launcher, air combo, special, super, pushblock, hitstop tuned. Debug overlay. *Gate: people who play MvC say it feels right.* |
| 2 | **Studio MVP** | Generate→normalize→QC→hitbox pipeline + timeline/frame-data editors. Character #2 built entirely through Studio in < 2 days. |
| 3 | **Online** | Rollback over WebRTC + match server with input ledger + server-side result verification. Playable cross-region < 100 ms with good feel. |
| 4 | **Single-player + roster** | FSM AI at 3 difficulties; roster to 4–6 characters via Studio + archetype pose libraries. |
| 5 | **Auth + coin-op** | Privy login, profiles, deposits → credit ledger, ranked queue. |
| 6 | **Wagering** | Escrow contract + verified-result settlement. Gated on legal review; testnet first. |

Milestones 0–1 are the whole ballgame: if the core doesn't feel like MvC with one character, nothing downstream matters. Estimated engineering weight: core+combat ≈ 35%, studio+pipeline ≈ 30%, netcode+server ≈ 20%, AI+meta ≈ 15%.

## 11. Prior art evaluated

**[chongdashu/vibe-fighter](https://github.com/chongdashu/vibe-fighter)** (evaluated 2026-07-14) — decision: **do not build on it; use as a reference for scope of Milestone 1 only.** Reasons: (1) no license file → all rights reserved by default, unusable as a foundation for a commercial/monetized product; (2) Phaser 4 scene-based architecture with game logic coupled to the framework — no deterministic, snapshot-able sim, so rollback netcode and server-side result verification (our anti-cheat/wagering backbone) would require a ground-up rewrite anyway; (3) zero netcode or server code — local 2-player keyboard only; (4) characters are hand-written per-character TypeScript classes (`redBrawler.ts` etc.), the exact "logic as code" pattern our declarative data format is designed to avoid; (5) the authoring tooling (Character Gym, Fighter Playground) is withheld behind the author's paid membership program — the one part adjacent to our differentiator isn't in the repo; (6) 2 commits, 7 stars — a demo, not a maintained engine. What it *does* validate: AI-generated fighters with per-frame hit/hurt/guard boxes in a browser at 60fps is achievable — roughly our Milestone 1 scope.

**[0x0funky/agent-sprite-forge](https://github.com/0x0funky/agent-sprite-forge)** (evaluated 2026-07-14) — decision: **adopt as the seed of §5's generation + normalization stages; it is not the whole pipeline.** MIT licensed → safe to vendor/fork. It's an agent skill (prompt playbook + a ~39KB deterministic Python post-processor) that generates sprite sheets via an agent's built-in image generation and then does chroma-key cleanup (#FF00FF), frame splitting, alignment, scale-drift/edge-touch QC, and transparent PNG/GIF export. Its prompt rules encode hard-won lessons that match our design (multi-row grids to prevent horizontal drift, centered-subject safe areas, stable feet anchor, scale matching vs accepted idle sheets — a lightweight version of our reference-sheet contract). **What we take:** the prompt-rules playbook (§5 stage 2), the post-processor as the starting point for our normalization pass (§5 stage 3), and its QC metadata as seeds for our QC gate (§5 stage 4). **What it doesn't cover (still ours to build):** reference-sheet identity conditioning across a full moveset, per-character palette lock/quantization, archetype pose libraries, CLIP/embedding similarity QC vs the reference sheet, auto-hitbox/hurtbox drafting, and export to our character bundle format (it emits PNGs/GIFs, not engine data). Caveats: 4 stars/0 forks (treat as vendored code we own, not a dependency we track), and it assumes an agent runtime with native image gen — Studio will call an image-gen API directly instead, reusing the same prompt contracts.

## 12. Risks

| Risk | Mitigation |
|------|------------|
| AI sprite consistency worse than hoped | Palette-lock + pixelation normalization hides most drift; archetype pose conditioning; budget manual touch-up time per character; QC gate keeps bad frames out |
| Determinism bugs (float leaks, iteration-order) | Fixed-point math from day 0, lint rules, CI replay-hash tests, cross-env verification |
| "Feels floaty / not MvC" | Hitstop/pushback/gravity are all data-tunable; Milestone 1 gate with genre players before scaling |
| Rollback retrofit pain | Rollback-native from Milestone 0 |
| Wagering regulatory exposure | Phased rollout, non-custodial escrow, legal review gate, credits-only until cleared |
| Scope creep toward full MvC systems | Tag/assist explicitly deferred; entity model keeps the door open cheaply |
