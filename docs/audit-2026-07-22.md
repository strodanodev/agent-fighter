# Build audit + v1.02_scale — 2026-07-22

Full audit of the current build (client, server, studio, core, infra) against
`docs/build-spec.md` (v1) and `docs/build-spec-v2.md` (as-built), followed by a
scoped hardening pass on branch `v1.02_scale`. Method: every claim read from
source (file:line), cross-checked against the live prod endpoint, the live
Supabase security advisors, and the two prior audits (2026-07-17, 2026-07-18).
Nothing assumed from docs or memory.

## Verdict

The build is **production-deployed with strong fundamentals and one hard scale
ceiling.** The deterministic core is genuinely excellent (integer fixed-point
with no float leaks, source-level guard test, cross-engine browser-vs-Node
golden gate). The credits/wager/arcade economy is well-architected (atomic
idempotent Postgres RPCs, append-only ledger) and the 2026-07-18 launch
blockers are fixed (self-match mint, verification DoS, JWT exp/partnerId, ws
maxPayload, character value-validation, lobby heartbeat — all re-verified at
HEAD).

What separates "deployed" from "production-grade at scale":

1. **Scale ceiling.** One Node process, one event loop, one CPU core; all live
   match/queue/arcade/resume state in RAM; verification runs as synchronous
   re-sims on the event loop; **no horizontal-scale path** (no shared runtime
   store, resume is instance-local). Realistic wall: order-of-hundreds of
   concurrent matches before settlement bursts stall every socket.
2. **Roster is one archetype.** All 18 characters share one move-id signature
   (verified: identical `d2dac836` across every bundle) — cosmetic breadth,
   little mechanical variety. Sprites are pipeline-generated; frame data is
   hand-seeded from one shoto skeleton and lightly diverged.
3. **M1 feel gate never run** (spec calls it "the whole ballgame").
4. **Ops thinness** — `console.log` only, no metrics/alerting on a money
   backend; keep-alive after uncaughtException; raw financial tables are
   world-readable at the PostgREST level (privacy leak, not takeover).

Spec drift worth stating plainly (all reconciled in v2): renderer is Canvas 2D
not PixiJS/WebGL; transport is a WebSocket relay not WebRTC P2P; the sim is
hardcoded 1v1 not the "tag-ready entity pool"; fixed-point is 24.8 not 16.16;
determinism replay is 100× not 1000×.

## v1.02_scale — what this branch changed

Scoped to high-value, low-risk, well-tested improvements. Deliberately NOT a
re-architecture (see deferred roadmap).

### 1. Scale: one settlement re-sim instead of two (`packages/server/src/server.ts`)

`finishMatch` used to run **two** full re-sims of the ledger from tick 0 per
settled match — `verifyLedger`/`verifySoloLedger` (derive the outcome) then
`findDeviator` (walk again checking client hashes). They stepped the identical
deterministic simulation, so they are now **one** `verifyAndScan` pass that
derives the outcome AND names the earliest-diverging deviator together. Halves
the event-loop time every settlement blocks for → roughly doubles the
concurrent-match ceiling. Behaviour is unchanged; covered by the existing
desync forensics tests (`test/dos.test.ts`: honest hashes → no deviator;
one corrupted hash → convicts side 0).

### 2. Scale/DoS: connection caps (`server.ts`)

The `clients` set was unbounded — a connection flood had no ceiling and no
per-IP limit. Added a global cap and a per-IP cap (env-tunable
`AF_MAX_CONNS` / `AF_MAX_CONNS_PER_IP`, defaults 5000 / 64), refusing over-cap
sockets with close code 1013 **before** they allocate a Client or join the
sweeps. Per-IP counter decremented on close. New test in `test/dos.test.ts`.

### 3. Client robustness: storage never white-screens (`packages/client/src/main.ts`)

`main.ts` read `localStorage` at module-eval (the remembered fighter). In a
sandboxed iframe / hardened-privacy context that throws `SecurityError` and
aborts the whole bundle before any error UI exists — a permanent white screen,
in exactly the embed contexts the game is shared into (dare/share links). All
`localStorage` access now goes through `safeGetItem`/`safeSetItem`/
`safeRemoveItem` wrappers that degrade to a no-op instead of crashing.

### 4. Security: lock down standalone SECURITY DEFINER RPCs (`supabase/migrations/0019_lock_definer_rpcs.sql`)

Revokes public/anon/authenticated EXECUTE on `house_agent_stats()` (called only
server-side with the service key) and `rls_auto_enable()` (unused by app code).
`win_streak(text)` is deliberately left — it is invoked inside the anon-granted
`agent_roster` view, so revoking it could break anon reads; documented for a
follow-up. **Not yet applied to prod** — apply via the SQL editor / `supabase
db push` after review (it is idempotent and reversible).

## Deferred on purpose — the real horizontal scale-out

Not built here because it forces the money-settlement path async and only pays
off far above current load (prod is at 0 concurrent right now). Documented so
it is a decision, not an omission:

- **Offload verification to a worker-thread pool.** The deterministic core has
  isolated module globals per worker, so re-sim can run off the event loop with
  no shared-state race. `finishMatch` becomes async; the arcade/item/referral
  settlement ordering must be preserved carefully. This is the true "add a
  core" fix.
- **Move live runtime state to a shared store (Redis) + sticky routing** so a
  second instance is useful: `queue`, `liveMatches`, `arcadeRuns`, and resume
  tokens are currently in-process, so two instances never match or resume each
  other. This is the only path past the single-core wall.
- **Second/third character archetypes** (zoner, grappler) — the roster's
  mechanical monotony is a bigger product risk than raw scale.
- **Structured logging + metrics/alerting** on settlement failures, escrow
  drift, and event-loop stalls before real stakes scale.
- **Curated public views** for `profiles`/`credit_ledger`/`matches` (hide
  `agent_key_hash`, wallet `address`, financial history from raw PostgREST) —
  coordinated change, no app client reads these directly today.

## Single-player pass (monetization deferred → depth over scale)

With real-money features on hold, the retention loop is single-player. The AI
was already strong (intents, reaction model, personality, adaptation, a combo
book derived from the cancel graph). The gaps were correctness + half-wired
features, fixed here — validated against the bot-vs-bot balance suite
(`core/test/ai.test.ts`) so the difficulty lever ("skill 85 beats skill 25")
never regressed.

### AI (`packages/core/src/ai.ts`)
- **`aiGrounded` read a hardcoded `fp(460)`** — a duplicate of `STAGE.floorYPx`
  that would silently break every AI grounded check (anti-air, super, jump-in)
  if a stage floor were ever retuned. Now reads `STAGE.floorYPx`.
- **`eatLow` was written but never read** (dead adaptation). Now classified from
  the connecting move's own hitbox `guard` (with stance fallback) and fed into
  the Defend appetite in `pickIntent` — mirroring how `eatThrow` already works —
  so a low-pressured AI genuinely starts blocking more.
- **`eatOverhead` (read, never written) and `guardHigh` (never used) removed.**
  Every overhead in this roster is a jump-in, already counted as `eatJump`, so a
  grounded-overhead counter is inert by construction — wiring it would fake a
  feature that can't fire. Removed rather than shipped dead.

### Arcade variety (`packages/server/src/server.ts`)
- Arcade opponents all share ONE moveset (the roster is a single archetype), and
  their personality was sampled at random. Now each fighter gets a **signature
  style** (rushdown / zoner / turtle / jumpy / grappler / all-rounder),
  deterministic by id, so the gauntlet feels varied and players learn a
  fighter's tendencies. The style ships in the match pin (`SMatch.solo`), so the
  client sim and the server re-sim build the identical AI — no desync. Values
  stay inside `AI_PERSONALITY_RANGES`. Test harness (`arcade.test.ts`) updated to
  build the house AI from the full pin (incl. personality), as the real client
  does.

Verify: typecheck ×4, core 97/97 (incl. balance lever), server suite green.

## Tuning features (Feel Lab + per-character overrides)

Two additions that make the game's feel authorable and testable.

### Feel Lab (`tools/feel-lab`, `npm run lab`)
A local bench embedding the real `@af/core` sim: live sliders for every global
`TUNING` knob (the sim reads `TUNING` each tick), feel diagnostics (move/phase/
frame, hitstop, combo scaling, juggle, input history), and an AI opponent picker
(skill + the arcade personality styles). `data.ts` `TUNING` became a mutable
object with `applyTuning`/`resetTuning` and a frozen `TUNING_DEFAULTS` — only the
Lab calls `applyTuning`; the shipped client and server verifier run the defaults,
so no online/verified match is affected.

### Per-character tuning overrides (archetype feel)
Most archetype feel is ALREADY per-character (bundle: walk/dash/jump/gravity/
air-dash/hurtboxes; per-move hitboxes: damage/hitstun/**hitstop**/**pushback**/
launch/juggle). The gap was a few genuinely-per-fighter knobs that were global.
A bundle may now carry an optional `tuning: CharTuning` overriding
`jumpSquatTicks` / `knockdownTicks` / `getupTicks` / `grabTicks` (nimble-vs-heavy
jump + wakeup, and a fast command grab). It ships IN the bundle → pinned +
content-hashed like the moveset, so both clients and the server re-sim load
identical values (deterministic, no desync). `loadCharacter` validates
(allowlisted keys, integer ≥ 1); the sim reads `ch.b.tuning?.X ?? TUNING.X` at
four single-fighter sites (no side-mapping). Shipped characters carry no `tuning`
→ golden replay byte-identical. The Feel Lab gained a per-character column.

- **What did NOT change (deliberately):** the genuinely-global knobs (round flow,
  damage scaling, meter cap) stay global; letting them differ per side would need
  a resolution rule and add no archetype value. Genuinely-new archetype mechanics
  (armor, a distinct command-grab type, air-dash variety) are engine features,
  not tuning — a separate effort.

### Access model (who can tune what)
- **`TUNING` (global feel/physics):** dev-only, via the Feel Lab, then baked into
  `data.ts`. Never network-exposed — shared physics both sides must agree on.
- **Per-character `tuning`:** authored in the bundle (Studio/data), pinned +
  hashed. Not player-editable at runtime.
- **AI personality (playstyle):** agent/Minds-coachable via `PUT /agent`
  (numeric knobs clamped to `AI_PERSONALITY_RANGES`, 30/hr). Skill is NOT
  coachable — it derives from account level (`skillForLevel`), so difficulty
  scales with LVL while feel stays constant.

Verify: typecheck ×4, core 103/103 (6 new tuning tests; golden green), server green.
