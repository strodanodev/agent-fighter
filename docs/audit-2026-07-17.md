# Build audit — 2026-07-17

Full audit of the current build against `docs/build-spec.md` (v1, 2026-07-14).
Method: verify gate run, spec walked section by section, prod health checked,
git history and working tree inspected.

## Verdict

Three days after the spec was written, **milestones 0–5 are code-complete and
milestone 6 (wagering) is substantially built** — against a spec that budgeted
those as the whole v1. The build is ahead of its own plan on scope and behind
it on validation. Nothing here is vapor: prod is live and healthy
(`match-server-production.up.railway.app` reports `persistence:true`, 12
characters, 3 stages, protocol 3; the Vercel client returns 200).

`npm run verify` is **green**: typecheck across all 4 packages, 67 core tests,
28 server tests.

## Confirmed spec deviations

Each of these is a real divergence from the written spec. Most are defensible;
they are listed so the choice is explicit rather than accidental.

1. **Renderer is Canvas 2D, not PixiJS v8/WebGL2** (spec §6). Declared openly
   in `packages/client/package.json` ("PixiJS planned"). Measured 1.9 ms/frame
   against a 16.7 ms budget, so the perf argument for Pixi has not materialised.
   Demo bundle is 332 KB against a < 5 MB spec ceiling. **Recommend: amend the
   spec, not the code.**

2. **Transport is a WebSocket relay, not WebRTC P2P** (spec §7.1). Rollback,
   prediction, and resim are all real and run over the relay; `net.ts:9` notes
   the machinery is transport-agnostic. Spec treats relay as the *fallback*.
   Note that the relay is currently what makes DDoS-the-opponent impossible
   (peers never learn IPs) — ADR 0005 already flags that P2P forfeits this.

3. **Snapshot ring is 128, spec says ~10** (`net.ts:25`). Harmless — larger is
   safer, and the ring-wrap hazard is already understood and bounded.

4. **Identity is AIR Kit (Moca), not Privy** (spec §9). Arguably an upgrade:
   AIR account doubles as the wallet. Spec §9's real obligation — "user
   identity flows through [an identity provider] from the start" — is met.

5. **No zod.** Spec §3 names zod explicitly; `data.ts` has a comment
   acknowledging the intent and hand-rolled validation in `loadCharacter()`
   (`data.ts:158+`) that throws on duplicate ids, empty steps, non-integer
   frames, missing buttons/motions/meterCost. Functionally equivalent for the
   fields it covers, with a dependency-free core preserved. **Low priority.**

6. **Entity model is NOT tag-ready** — see red flags below. This is the one
   deviation the spec explicitly argued against in advance.

7. **Charge moves are absent** (spec §4 lists them alongside 236/214/623).
   No character needs them yet. Cosmetic gap in coverage, not a defect.

8. **"Insert coin" mints, it does not deposit** (spec §9 Phase B: on-chain
   deposit → off-chain credit ledger). Credits enter via a daily +10 grant.
   There is no cash-out, which is what currently keeps this out of regulatory
   scope — and also what makes it not yet the spec's coin-op.

9. **Ledger signatures unimplemented** (spec §9 Phase C: "both players'
   clients + server sign the input-log hash"). Signing infrastructure exists
   (`air-issuer.ts`, `airjwt.ts`) but is pointed at credentials, not ledgers.
   Correctly not-yet-due — but it is a hard prerequisite for real wagering.

## Red flags

**1. The M1 feel gate has never been run. This is the top risk in the project.**
Spec §10 is unusually blunt: *"Milestones 0–1 are the whole ballgame: if the
core doesn't feel like MvC with one character, nothing downstream matters."*
Five milestones — Studio, 12 characters, netcode, economy, wagering — are now
stacked on a foundation whose stated acceptance test has not been attempted.
Zero external playtests exist. Every hour spent on sprite pipelines and escrow
SQL is leveraged on an unvalidated assumption, and the tuning knobs (`TUNING`,
per-character frame data) get harder to move as the roster grows: retuning
against 1 character was cheap, against 12 it is a project.

**2. Concurrent sessions are editing `@af/core` live.** During this audit
`verify` went red with `Cannot find name 'SUPER_SKILL_FLOOR'` at a line number
that did not match the file on disk; `ai.ts` had been written 23 seconds
earlier. Re-running was green. That was a race with another session mid-write —
not a breakage, but it means **the working tree is not a stable audit target**,
and two agents editing the deterministic core concurrently is exactly how a
golden-hash conflict or a lost fix happens. Seven files are uncommitted,
including a new `autospecial.ts`.

**3. No cross-environment determinism test — the highest-consequence untested
claim in the build.** Spec §2.1 demands the CI gate assert bit-identical hashes
*"cross-environment (browser vs Node)"*. What exists is Node-only: golden replay
hashes, mechanical guards banning `Math.random`/`Date`/DOM/timers, serialize and
snapshot completeness. All excellent, all one environment. The entire money
path assumes a browser sim and a Node re-sim agree bit-for-bit; if they ever
drift, honest players get flagged as deviators and forfeit real credits. This
has been proven *empirically* (live matches verified, no deviator, 4918-tick
match bit-identical) but is not *gated*. Empirical evidence expires the next
time someone touches sim arithmetic.

**4. The economy is live with an open farming surface.** Real credits, real
Supabase, real settlement. The sybil/rate-limit knobs flagged in ADR 0004 are
still open: nothing observed stops N accounts each claiming +10/day. This is
tolerable only because credits cannot cash out — that property is now
load-bearing and should be treated as a release gate, not an implementation
detail.

**5. Escrow orphaning is fixed; the class of bug it came from is not.** The
sweeper (migration 0003) is correct and live-smoked. But the underlying lesson
from the memory record — `NULL = s` is NULL, not false, and it settled *both*
sides as losers on real Postgres — says money logic lives twice (SQL + the TS
mirror in `persist.ts`) and the TS mirror cannot catch SQL semantics. Every
future money change needs a real-Postgres smoke test, not a passing test suite.

**6. `main.ts` (1190 lines) and `ui.ts` (1951 lines) are accreting.** Already
noted as "fights back" in the project record. Not urgent, but the VS-card /
wallet / stakes work all landed here and the next UI feature will hurt.

**7. VS poses authored for 1 of 12 characters.** Analog only. The other 11 fall
back to select portraits, which is safe but inconsistent — the exact bug the
VS-slot work was built to fix.

## What is genuinely strong

Worth stating plainly, because an audit that only lists problems misleads:

- **Determinism discipline is better than the spec asked for.** `guards.test.ts`
  mechanically bans the entire hazard class (`Math.random`, `Date`, DOM,
  timers, `fetch`, `process`, transcendental math) rather than trusting review.
  `serialize.test.ts` proves *every* scalar field reaches the hash by mutating
  each one. Golden hashes pin 6 full matches. This is the part most projects
  fake and this one didn't.
- **`autospecial.ts` is a model of the architecture paying off.** It gives
  tap-to-special by *synthesising buttons through the normal `InputFrame` path*
  — it cannot desync, works under rollback and online for free, and required
  zero core changes, because the spec's `InputSource` abstraction was actually
  honoured. Its header comment reasons from the server-reverify constraint
  correctly.
- **Secrets hygiene is clean.** `.env`, `air/partner_rs256.pem`, `vendor/`,
  tool binaries all gitignored; only `.env.example` and the keygen tool tracked.
- **Zero TODO/FIXME/HACK markers** across all four packages' source.
- **The settlement ladder (ADR 0005) is real engineering.** "The ledger is the
  truth" correctly makes winning-then-disconnecting safe and ragequitting
  unprofitable — the non-obvious right answer.
- **M2's exit test didn't just pass, it embarrassed the budget:** < 2 days
  allowed, ~5 minutes actual.

## Recommendations — in priority order

**P0 — Run the M1 feel gate this week, before anything else ships.**
It is now practical solo via VS AGENT and the loop is polished (quick match,
rematch). Get 2–3 people who actually play MvC in front of the Vercel build and
have them answer one question: does it feel right? This is the spec's own
blocking gate, it is the cheapest it will ever be, and it is the only item here
that can invalidate the other 5 milestones. If it fails, everything else waits.

**P1 — Land a cross-environment determinism gate.** Run the golden scenarios in
a headless browser in CI and assert the hashes match the Node ones. This closes
the one spec-mandated gate that is missing, and it is the gate the money path
silently depends on. Without it, the first float leak becomes a support ticket
from a player who lost credits, not a red build.

**P2 — Serialise the concurrent-session problem.** Commit or shelve the seven
in-flight files, then establish that one session owns `@af/core` at a time.
Two agents editing the deterministic core concurrently will eventually produce
a golden-hash conflict that looks like a determinism bug and isn't.

**P3 — Close the economy knobs before any cash-out conversation.** Sybil rate
limits and a solo-farm cap (both already named in ADR 0004). Treat "credits
cannot cash out" as an explicit, written release gate — it is currently the
only thing standing between this build and regulatory scope.

**P4 — Amend the spec to match reality.** Canvas 2D over Pixi, relay over
WebRTC P2P, AIR over Privy, hand-rolled validation over zod. All four are
defensible; leaving them undocumented means a future agent (or Grok in Cursor)
"fixes" the code to match a stale spec. Cheapest task on this list.

**P5 — Housekeeping.** VS poses for the remaining 11 characters; split `ui.ts`
/ `main.ts` when they next fight back; decide explicitly whether tag/assist is
ever happening (see below).

## Open question worth deciding now

**Is tag/assist actually in the future?** Spec §2.2 is emphatic: *"Do not
hardcode 'player 1 fighter' and 'player 2 fighter'"* — the sim was supposed to
own an entity pool with teams owning fighter lists, so tag ships later without
an engine rewrite. What exists is `fighters: [FighterState, FighterState]`
(`state.ts:103`) — a hardcoded 2-tuple, threaded through `snapshot`/`restore`/
`serialize` and the golden hashes.

This is the one deviation the spec argued against *in advance*, and the reason
it gave was that retrofitting is a rewrite. That reason still holds, and the
cost is now higher: the tuple is baked into the hash format that the server,
the golden tests, and every settled match agree on.

So decide deliberately rather than by drift:
- If tag/assist is genuinely a someday-feature, **write that off now** in an
  ADR. The 2-tuple is simpler and it is working; pretending otherwise is worse.
- If it is real, the refactor only gets more expensive with every character,
  every golden hash, and every match settled against the current format.

Do not leave this ambient. Right now the spec claims tag-ready and the code
isn't, which is the most expensive of the three states.
